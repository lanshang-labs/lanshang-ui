# AI 前端开发与接手流程

这是 Lanshang 所有的公共前端工作流；入口仍是 [前端指南](frontend.md)。它组合已有工具，不建立额外 CLI、DSL、任务数据库或强制 Skill。devctl 的已实现发现／声明／预览合同见其项目内 `doc/command/design/README.md`，具体行为以项目当前 CLI 为准。

## 1. 读取事实与范围

读取目标项目 AGENTS、Design.md、package.json、lockfile、原生工程入口及当前 Git 改动。采用 devctl 时运行 `devctl project show --json` 与显式 target 的 `devctl design context --workspace <项目根> --target <前端目录> --json`；它们不下载外部指南，AI 仍需主动读取本仓库前端指南。缺少 Design.md 时按确认需求形成最小声明，不从相邻平台复制业务合同。

默认采用 Lanshang。项目可以在自己的 Design.md 正文中维护明确差异；Agent 在声明的适用范围内遵守项目选择，未声明部分继续按 Lanshang。差异可以涉及品牌、配色、密度、布局、交互或已有技术栈，不要求新增 schema、复制整套规范或为普通项目差异另建审批流程。具体说明见[默认规范与项目差异](frontend.md#默认规范与项目差异)。

新建目录尚未登记时，先区分“没有有效登记声明”和“有效声明明确禁止”；不要把未登记空视图的权限零值误读为已读取的禁止策略。用户明确授权的新项目可按原生工程方式起步，仍遵守任务边界；不为通过观察命令自动修改全局 Registry、伪造治理状态或绕过受控写入守卫。有效登记的明确限制、声明不完整和读取失败分别按 devctl Project 合同处理。未采用治理或 Boomerang stack 的观察失败保留为真实缺口，不声称已通过或已采用。

默认验证基线是 React／React DOM 18.3.1、Ant Design 5.22.5、TypeScript；复用项目已有路由和请求层。已有项目先核对实际技术栈，不因框架采用自动升级 React、重建工程或换 UI 底座。

### devctl 与 Lanshang 的接手链路

使用 devctl 组织全栈开发时，前端阶段继续使用已有命令：

```sh
devctl design context --workspace <项目根> --target <前端目录> --json
devctl design check --workspace <项目根> --target <前端目录> --json
devctl design preview --workspace <项目根> --target <前端目录> --json
```

`context` 用于读取项目声明与接手入口，`check` 只验证声明和路径，`preview --json` 只取已声明的启动计划。它们不代替阅读公共指南、执行项目原生检查或浏览器验收，也不因命令成功推断已经采用某个主题／组件。源码 CLI、安装态 CLI 及其构建内置文档可能不同，实际调用的 producer 和输出分别记录。

本仓库的实际入口为根 [Design.md](../Design.md)，可用样例与本地候选边界见 [目录说明](showcases.md)。对其他项目显式选择子目标时，只读取该目标，不向上寻找 package.json、lockfile 或启动命令；仓库级工程事实从明确选择的根入口再读。子目录没有独立启动声明时，按根声明复用已有预览，不虚构命令、不放宽路径边界。`examples/product-workbench` 完整应用样板仍是本地候选，未包含在本次文档交付中。

项目 Design.md 正文记录实际采用的规范修订、样板来源、品牌差异，以及 package.json／lockfile／固定产物和原生验证入口；声明、锁定依赖、已安装内容、实际兼容验证分别提供证据。未记录的信息明确为未记录，不能从文件存在、文档链接或本地源码推导正式发布与兼容性。外部规范由 Agent 按链接读取，devctl 不保存公共 UI 规则或版本表。

## 2. 明确平台设计语言

从产品任务选择管理、创作、资源或阅读布局。记录品牌／Logo、界面配色、密度、主要导航、允许差异及真实状态；使用 [品牌设计范例](brand-design.md) 比较方案。公共规则由 Lanshang 维护，消费者 Design.md 记录本平台的具体选择。

品牌设计不等于把页面涂成品牌色，也不要求不同平台外形完全相同。同语义控件、图标、焦点、操作和反馈应一致；内容与业务流程保留产品差异。

## 3. 获取参考并选择共享组件

先检查实际固定包 exports、文档与现有模板。21st CLI/MCP 可搜索、读取视觉参考，取回后按具体来源核对许可；不因检索新组件而安装另一套运行时。没有需求时不调用付费 AI 生成或购买第三方模板。

复杂表单、表格、选择、树、弹层和焦点使用 AntD 成熟能力；Lanshang 统一视觉、公开组合、主题、图标和特色组件。没有封装的 AntD 能力可以在共享 Provider 下使用，不要求为所有 API 再造包装；共性视觉修正先反馈到 Lanshang。

## 4. 组合真实交互

应用使用一个根 Provider，固定包版本；业务拥有路由、请求、权限、校验、状态机、幂等与恢复。页面只维护业务排布与明确的品牌差异，不复制共享组件 CSS 或用主题切换重挂载页面。

覆盖有内容、首次读取、成功空结果、刷新、失败和恢复。刷新保留最后成功快照和草稿，未知业务结果先核对原操作，不能用等待动画推断成功。视觉优先仍保留必要名称、危险确认和对象说明。

## 5. 验证与独立审核

使用消费项目自己的类型检查、定向测试、构建和预览；检查浅暗／所选配色、目标窄屏、长内容、键盘、Portal 和草稿／选择保留。组件目录与状态对照以该版本实际存在的文档站路由、catalog 和固定包类型为准，本次接手文档不新增站点页面。

审核聚焦真实差异和重要交互。机械检查不判断美感，截图不证明权限／业务成功；记录已验和未验范围，不为每个小改动创建全量审查门槛。

## 6. 交付与采用

记录修改、原生验证、来源许可和剩余缺口。公共包候选、正式发布、平台依赖升级、部署和用户验收分别成立；不能从源码预览或文档存在推断平台已具备未发布 API。devctl 不保存第二套版本表，消费者锁定实际依赖并验证。

需要更新时，公共规则、组件与图标回到 Lanshang；路由、权限、业务状态和品牌采用留在消费项目。保留原资产、已有反馈和未改动工作。

## 可直接交给 AI 的接手提示

> 本项目默认采用 Lanshang UI，遵守项目 Design.md 中明确的差异；未声明部分继续沿用 Lanshang。先读项目 AGENTS、Design.md、lockfile，以及 Lanshang doc/frontend.md；按任务读取 design、icons、brand-design、component-usage 和实际组件 API。沿用当前技术栈与业务路由，以固定版本 Lanshang 组件及受其 Provider 管理的 AntD 能力组合页面。品牌、布局与业务差异记录在本项目 Design.md，共性视觉问题回到 Lanshang。先完成可操作候选和原生验证，再分别记录发布、采用和部署；不要把实验 API 当成正式包能力。
